# Bug Investigation: TDD Loop After Refactor Phase Failure

## Symptom

User reported Gromit getting stuck in an "endless TDD loop" and cancelled after the third iteration. The last run (`run-20260221-162703.jsonl`) shows bead `gromit-73tlv` ("Implement Review stage with config-gated LLM review and bead creation") cycling through RED phase repeatedly:

- **Iter 1**: `gromit-73tlv` → `error: "refactor phase failed"` (7m 17s, $2.09, 9 files touched, sonnet)
- **Iter 2**: `gromit-73tlv` → `error: "red phase: context cancelled"` (3s, opus, `compilation_errors: true`)
- **Iter 3** (next run): `gromit-73tlv` → same context cancellation

## Root Cause

When the TDD refactor phase **invocation fails** (as opposed to "refactor broke tests"), the orchestrator returns `refactorOutcomeFailed` without performing any git reset. The GREEN phase changes are left uncommitted in the working tree.

**Code path** (`internal/runner/tdd/orchestrator.go:239-271`):

```go
func (o *CycleOrchestrator) executeRefactorPhase(...) refactorOutcome {
    preRefactorCommit, _ := o.getGitHeadFn()   // captures post-GREEN HEAD

    if err := o.runRefactorFn(ctx, bc); err != nil {
        return refactorOutcomeFailed              // ← NO RESET HERE
    }
    // ... tests-broke path does reset to preRefactorCommit
}
```

The "refactor broke tests" path correctly resets to `preRefactorCommit`. The "refactor invocation failed" path does not.

**Consequence**: The next iteration starts with:
1. `bc.StartCommit` = post-GREEN HEAD (dirty, may include compilation errors)
2. Pre-build check detects `compilation_errors: true` (confirmed in iter 2 log)
3. RED phase runs against partially-implemented code in an inconsistent state
4. The bead will fail again, repeating the cycle until `StuckBeadThreshold` (3) is reached

This bead (`gromit-73tlv`) is a large architectural refactor (14 TDD coverage criteria, restructures `internal/runner/`). The GREEN phase wrote 9 files with partial code that didn't fully compile—which is why the refactor phase existed: to complete/clean up the implementation. When refactor fails, the partial code is left behind.

## Affected Code

- `internal/runner/tdd/orchestrator.go:239-271` — `executeRefactorPhase`: handles `refactorOutcomeFailed` without reset
- `internal/runner/process_methodology.go:115-129` — `runTDDFreshContextCycles`: TDD failure path also has no reset
- `internal/runner/run_iteration.go:409-432` — bead failure handling: no reset before retry

## Suggested Fix

**Option A (targeted)**: In `executeRefactorPhase`, when refactor invocation fails, reset to `preRefactorCommit` (post-GREEN state, tests passing). This preserves GREEN work and only discards the failed refactor attempt.

```go
if err := o.runRefactorFn(ctx, bc); err != nil {
    if preRefactorCommit != "" && o.gitResetFn != nil {
        _ = o.gitResetFn(preRefactorCommit)
    }
    return refactorOutcomeFailed
}
```

**Option B (robust)**: In `runTDDFreshContextCycles`, when the TDD cycle fails entirely, reset to `bc.StartCommit`. This ensures every retry starts from a completely clean working tree.

```go
if err := r.tddOrchestrator.RunCycles(ctx, bc, coverageTracker, coverageCriteria); err != nil {
    if bc.StartCommit != "" {
        if resetErr := r.resetHard(bc.StartCommit); resetErr != nil {
            r.log("Warning: failed to reset after TDD failure: %v", resetErr)
        }
    }
    bc.Result.Error = err
    return true
}
```

Option B is preferred because Option A still leaves the Green changes in place (with possible compilation errors), making RED phase on the next retry confusing. Option B guarantees a clean working tree for each retry.

The same reset should be applied to the coverage-incomplete failure path at `process_methodology.go:126-129`.
