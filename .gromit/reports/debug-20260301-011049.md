# Bug Investigation: Integration Queue Grows Without Draining

## Symptom
The integration queue keeps getting longer instead of draining as runs complete.

Observed in current workspace snapshot (`.gromit/integration-queue.json`):
- 8 total entries
- 6 in `ready`
- 2 in `draft`
- no `integrating` or `merged`

The queue is receiving entries from session completion, but they are not being integrated out of `ready`.

## Root Cause
The runner-level integration coordinator used in production is a stub implementation that does nothing.

Details:
- Session completion intentionally enqueues branches and defers integration to the orchestrator coordinator.
- Orchestrator does call `Coordinator.Coordinate(...)` between successful iterations.
- However, constructor wiring injects `runner.NewIntegrationCoordinator()`, whose `Coordinate` and `RecoverFromCrash` methods both return `nil` without touching queue state.

Result: queue entries are added (`draft -> ready`) but never processed (`ready -> integrating -> merged/conflict/...`), so queue length monotonically increases.

## Affected Code
- `cmd/gromit/interactive_worktree.go:224` (single-writer handoff contract; enqueue-only session path)
- `internal/runner/orchestrator.go:663` (run-loop calls coordinator between iterations)
- `internal/runner/constructor.go:306` (wires stub coordinator into orchestrator config)
- `internal/runner/coordinator.go:17` (stub `Coordinate` implementation)
- `internal/runner/coordinator.go:25` (stub `RecoverFromCrash` implementation)

## Suggested Fix
Replace the stub runner coordinator wiring with a real adapter over `internal/integrationqueue.Coordinator`:
- Build an `integrationqueue.Store` at startup (`.gromit` path).
- Provide a production `integrationqueue.GitOps` implementation for fetch/rebase/merge/push/cleanup using existing runner git/process abstractions.
- Provide a production `integrationqueue.ScopedGate` implementation invoking the configured validation/scoped-gate flow.
- Wire these into `integrationqueue.NewCoordinator(...)` and inject that concrete coordinator into `OrchestratorConfig`.
- Add constructor + orchestrator integration tests proving one `ready` entry transitions out of `ready` after a successful iteration.

## Evidence
- Queue handoff intent is explicit: `cmd/gromit/interactive_worktree.go:224` comment states sessions enqueue and do not merge directly.
- Orchestrator invokes coordinator post-iteration: `internal/runner/orchestrator.go:663`.
- Production wiring uses stub: `internal/runner/constructor.go:306`.
- Stub coordinator methods are TODO no-ops: `internal/runner/coordinator.go:17-20`, `internal/runner/coordinator.go:25-28`.
- Current queue snapshot indicates backlog accumulation in `ready` state with no drain transitions.
