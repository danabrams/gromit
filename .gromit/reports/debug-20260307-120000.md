# Bug Investigation: run2 rerun replans and redecomposes, losing progress

## Symptom

When `gromit run2` fails (e.g. acceptance failure) and the user reruns it with the same spec, the pipeline replans and redecomposes from scratch. This discards all prior bead progress — beads that were already completed are orphaned and new duplicate beads are created.

## Root Cause

`SpecLoop.Run()` in `internal/v2/loop/spec_loop.go:186` unconditionally executes the full stage pipeline: plan -> decompose -> build -> accept -> present. There is no resume detection.

Specifically:
1. **Plan stage** (`internal/v2/stage/plan/plan.go`) always invokes the LLM to generate a fresh plan. It never checks whether `.gromit/v2/plan.md` already exists in the worktree from a prior run.
2. **Decompose stage** (`internal/v2/stage/decompose/decompose.go`) always creates fresh beads via `tracker.CreateBead()`. It never checks whether beads with the `spec:<id>` label already exist in the task tracker.

Both stages follow the "fresh context each iteration" principle — but that principle applies to Claude *invocations*, not to structural artifacts like plans and bead decompositions that should persist across reruns.

## Affected Code

- `internal/v2/loop/spec_loop.go:186-287` — `SpecLoop.Run()` orchestrates the pipeline with no resume logic
- `internal/v2/loop/spec_loop.go:307-316` — `runPlanStage()` always invokes plan
- `internal/v2/loop/spec_loop.go:289-305` — `runDecompose()` always invokes decompose
- `internal/v2/stage/plan/plan.go` — plan stage has no existing-plan check
- `internal/v2/stage/decompose/decompose.go` — decompose stage has no existing-bead check

## Suggested Fix

Add resume detection to `SpecLoop.Run()`:

1. **Before plan stage**: Check if a plan file already exists in the worktree (e.g. `.gromit/v2/plan.md`). If it does, read and reuse it instead of invoking the LLM.
2. **Before decompose stage**: Query the task tracker for existing beads with the `spec:<specID>` label (using `ListWithLabel` or `ReadyWithLabel`). If beads exist, skip decomposition and feed them directly into the bead loop.
3. **Bead loop already handles partial completion**: The bead runner processes beads based on their tracker status (ready vs done), so reusing existing beads naturally resumes from where the previous run left off.

This preserves "fresh context each iteration" for Claude invocations while reusing structural artifacts (plan text + bead decomposition) that don't need regeneration.

## Evidence

- `SpecLoop.Run()` has no conditional logic around plan/decompose — always runs both sequentially (lines 221-244)
- Plan stage always calls `s.llm.Invoke()` and writes plan.md
- Decompose stage always calls `s.tracker.CreateBead()` for each decomposed bead
- Beads are labeled with `spec:<id>` (decompose.go line 258) but this label is never queried before decomposition
- `bead.Client` has `ReadyWithLabel()`/`ListWithLabel()` APIs that could be used for existing-bead detection but are not called in the spec loop or decompose stage
- The worktree is preserved on failure (`preserveOnFailure: true`, line 502) — so the plan file survives, but is never consulted on rerun
