# Bug Investigation: TDD fresh-context orchestrator short-circuits non-TDD beads

## Symptom

Three beads (`gromit-f37u5`, `gromit-3ffh0`, `gromit-0397i`) were closed as "successful" in the run starting at 14:25 UTC on 2026-02-19, but:
- Cost was $0.00 with 0 input/output tokens for all three
- No `provider` field was set in the iteration log (LLM was never invoked)
- Stream log (`stream-20260219-142512.log`) was empty
- No git commits were produced
- Durations (39-72s) matched validation-only time (go test/vet/build)
- Pre-existing uncommitted diffs in the working tree passed validation, creating the illusion of completed work

### Affected Beads

| Bead | Title | Model | Duration | Cost | Tokens |
|------|-------|-------|----------|------|--------|
| gromit-f37u5 | Fix nil pointer dereference in createRefinePipeline | opus | 72s | $0 | 0/0 |
| gromit-3ffh0 | Use path resolve helpers consistently in review.go | sonnet | 39s | $0 | 0/0 |
| gromit-0397i | Fix codex provider token reporting (all showing 0) | sonnet | 40s | $0 | 0/0 |

## Root Cause

A chain of four conditions combined to skip the LLM build phase entirely:

### 1. Global TDD config enabled without per-bead labels

`gromit.yaml` has:
```yaml
methodology:
  tdd: true
  fresh_context_per_cycle: true
```

These three beads (bug fixes from code review) had no `tdd:true` or `tdd:false` label.

### 2. IsActive falls back to global config

`internal/runner/policy/methodology.go:44-70` — `IsActive(labels, "tdd")` scans labels for `tdd:true`/`tdd:false`. Finding neither, it falls back to `p.cfg.Methodology.TDD` which is `true`. So TDD was active for all three beads despite them not being TDD work.

### 3. FreshContextPerCycle routes to TDD orchestrator

`internal/runner/process_methodology.go:62-67`:
```go
tddActive = r.methodologyPolicy.IsActive(bc.Bead.Labels, "tdd")
if tddActive {
    if r.cfg.Methodology.FreshContextPerCycle {
        r.runTDDFreshContextCycles(ctx, bc)
        return atddActive, tddActive, true  // done=true → skips normal build loop
    }
}
```

Because `tddActive=true` and `FreshContextPerCycle=true`, the code calls `runTDDFreshContextCycles` and returns `done=true`, which causes `processBead` to return immediately without entering `executeBuildAndMethodologyLoop`.

### 4. Empty ExpectedOutputs causes immediate completion

`internal/runner/callbacks.go:648-649` (in `makeTDDOrchestrator`):
```go
state := tdd.CycleState{
    Done: len(bc.Bead.ExpectedOutputs) == 0,  // true for bug-fix beads
}
```

`internal/runner/tdd/orchestrator.go:85-92`:
```go
func (o *CycleOrchestrator) RunCycles(ctx context.Context, bc *runtypes.BeadContext, state CycleState) error {
    for !state.IsComplete() {  // IsComplete() returns true immediately
        // ...never enters loop
    }
    return nil
}
```

`internal/runner/tdd/handoff.go:36-38`:
```go
func (c CycleState) IsComplete() bool {
    return c.Done || c.CycleNumber >= c.MaxCycles || len(c.Remaining) == 0
}
```

Bug-fix beads have no `ExpectedOutputs`, so `Done=true` from initialization. `RunCycles` returns nil immediately — zero cycles, no LLM invoked.

### 5. Validation passes on pre-existing diffs

Back in `runTDDFreshContextCycles` (`process_methodology.go:80-97`):
```go
if err := r.tddOrchestrator.RunCycles(ctx, bc); err != nil { ... }  // returns nil
if r.cfg.Validation.Enabled && r.validationRunner != nil {
    if err := r.runValidationWithRecoveryForStage(ctx, bc, true); err != nil { ... }
}
bc.Result.Success = true
bc.Result.FirstPassSuccess = true
```

The validation runner executes `go test/vet/build` against the working tree, which contains pre-existing uncommitted changes from prior work. These pass, so `Success=true` is set.

- `internal/runner/decompose.go:217` — calls `injectMethodologyLabels(b.Labels)`

Children inherit the parent's explicit label. No gap here.

## Suggested Fix

The immediate fix (applied) was to add explicit `tdd:true` or `tdd:false` labels to all open beads so the global fallback is never reached. However, this is a band-aid — the underlying design issue remains:

### Design Issue

The TDD orchestrator assumes all TDD-active beads have `ExpectedOutputs`. When a bead reaches the TDD fresh-context path without expected outputs, it silently succeeds with no work done. This is a silent data loss scenario.

### Recommended Code Fix

In `runTDDFreshContextCycles` or the `makeTDDOrchestrator` callback, add a guard:

```go
// In makeTDDOrchestrator, before RunCycles:
if len(bc.Bead.ExpectedOutputs) == 0 {
    return fmt.Errorf("TDD fresh-context requires ExpectedOutputs but bead %s has none; falling back to standard build", bc.Bead.ID)
}
```

Or more defensively, in `runTDDFreshContextCycles`:

```go
func (r *Runner) runTDDFreshContextCycles(ctx context.Context, bc *runtypes.BeadContext) {
    if len(bc.Bead.ExpectedOutputs) == 0 {
        bc.Result.Error = fmt.Errorf("TDD fresh-context-per-cycle active but bead has no ExpectedOutputs; aborting to prevent silent no-op")
        return
    }
    // ... existing code
}
```

This would cause the bead to fail loudly rather than silently succeed, forcing the operator to either add expected outputs or label it `tdd:false`.
