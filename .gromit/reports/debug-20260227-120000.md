# Bug Investigation: Fork Failure (EAGAIN) After ~12 Iterations

## Symptom

At iteration 12, all process spawning fails with "resource temporarily unavailable" (EAGAIN, errno 11). Affected binaries: `claude`, `codex`, `git`, `bd`, and even shell (`zsh: fork failed`). The Rust tokio runtime inside codex also cannot spawn worker threads. The system is completely unable to create new processes or threads.

Error messages observed:
- `fork/exec /home/dabrams/.local/bin/claude: resource temporarily unavailable`
- `fork/exec .../codex: resource temporarily unavailable`
- `fork/exec /bin/git: resource temporarily unavailable`
- `fork/exec .../bd: resource temporarily unavailable`
- `OS can't spawn worker thread: Resource temporarily unavailable (os error 11)`
- `zsh: fork failed: resource temporarily unavailable`

## Root Cause

**Cgroup PID limit exhaustion.** The system cgroup limits PIDs to 8137 (`/sys/fs/cgroup/pids.max`). After ~12 iterations, accumulated processes/threads from LLM CLI tool calls exhaust this limit.

### Contributing Factors (ordered by impact)

1. **LLM CLI grandchild process group escape** — Claude CLI and Codex CLI spawn subprocesses internally (via their Bash/tool calls: `go test`, `go build`, etc.). These grandchild processes may create their own process groups. Gromit's `ReapProcessGroup` sends SIGKILL to the LLM CLI's process group (`-pgid`), but grandchildren in separate process groups survive. After 12 iterations, escaped grandchild processes accumulate.

2. **No EAGAIN detection in failure triage** — `internal/runner/escalation/triage.go:31` only matches `no space left on device` for `resource_exhausted`. The pattern "resource temporarily unavailable" is not matched, so gromit treats EAGAIN as an unknown failure and continues iterating (making the situation worse).

3. **bd commands lack context timeout** — `internal/bead/bead.go:431-447` uses `exec.Command()` without context. If bd hangs (network, database lock), the calling goroutine blocks indefinitely with open file descriptors.

4. **No between-iteration resource monitoring** — No check on PID count, goroutine count, or file descriptor usage between iterations. Gromit has no way to detect resource pressure before it becomes fatal.

5. **git diff lacks context timeout** — `internal/runner/cmd_run.go:86-93` uses `exec.Command("git", "diff", ...)` without context.

### Why Iteration 12?

Each iteration spawns: 1-2 LLM CLI processes, each of which internally spawns multiple tool-call subprocesses (go test with N package binaries, go build, go vet, git operations). With GOMAXPROCS=4, each Go tool spawns up to 4 OS threads. A single `go test ./...` on this codebase could spawn 50+ test binaries × 4 threads = 200+ threads. After 12 iterations with imperfect cleanup: 12 × ~500 threads/iteration = ~6000 accumulated PIDs, plus the current iteration's processes, exceeds the 8137 limit.

## Affected Code

- `internal/procutil/procutil.go:38-44` — `ReapProcessGroup()` only kills the immediate process group; grandchildren in separate groups survive
- `internal/bead/bead.go:431-447` — `runWithEnv()` uses `exec.Command` without context timeout
- `internal/runner/cmd_run.go:86-93` — `getGitDiff()` uses `exec.Command` without context
- `internal/runner/escalation/triage.go:31` — `noSpacePattern` doesn't match EAGAIN errors
- `internal/runner/orchestrator.go:236-495` — main loop has no resource monitoring between iterations

## Suggested Fix

Multi-pronged approach (5 tasks, see plan):

1. **Add EAGAIN/fork-failure detection to triage** — so gromit stops iterating when resource-exhausted instead of making it worse
2. **Add recursive process tree kill** — walk `/proc/<pid>/task/*/children` to find and kill grandchildren that escaped the process group
3. **Add context timeout to bd commands** — propagate cancellation to prevent hangs
4. **Add context timeout to git diff** — minor but closes a gap
5. **Add between-iteration PID monitoring** — read `/sys/fs/cgroup/pids.current` and warn/stop when approaching the limit

## Evidence

1. **Cgroup PID limit**: `/sys/fs/cgroup/pids.max` = 8137, `ulimit -u` = 27123. The cgroup limit is the binding constraint.

2. **Both providers attempted**: The log shows both `claude` and `codex` being invoked with the same prompt (2301 bytes), indicating provider fallback occurred — the first provider failed, then the second also failed with EAGAIN.

3. **Universal failure**: Every binary fails (`claude`, `codex`, `git`, `bd`, `zsh`), confirming system-wide PID exhaustion rather than a single-process issue.

4. **Tokio thread failure**: `OS can't spawn worker thread: Resource temporarily unavailable (os error 11)` — even creating OS threads fails, not just fork/exec. This is characteristic of cgroup PID limits (which count threads as PIDs).

5. **No EAGAIN pattern match**: `internal/runner/escalation/triage.go:31` only has `noSpacePattern = regexp.MustCompile("no space left on device")`. There is no pattern for "resource temporarily unavailable" or EAGAIN.

6. **bd lacks timeout**: `internal/bead/bead.go:432` uses raw `exec.Command(c.binary, args...)` — no `CommandContext`, no deadline, no process group management.

7. **Process group kill is shallow**: `procutil.ReapProcessGroup` sends `SIGKILL` to `-cmd.Process.Pid` (the process group), but LLM CLIs like Claude Code create nested process groups for their own subprocess management, so grandchildren escape.
