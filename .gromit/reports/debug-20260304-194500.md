# Bug Investigation: Dirty worktree cascading failure blocks spec branch checkout

## Symptom

During a gromit run (non-session-worktree mode), iteration 20 fails with:
```
dirty worktree precondition blocked branch checkout for gromit/spec-fix-stale-worktree-branch-checkout:
dirty worktree .: M cmd/gromit/main.go\nM cmd/gromit/run_spec_flag_test.go.
Please commit, stash, or clean your working tree before switching branches.
```

The run terminates because dirty worktree errors cause a fail-fast return from `Run()`. The dirty files were left by a previous failed iteration.

## Root Cause

**Missing worktree cleanup after failed iterations in spec-branch mode.**

When the orchestrator uses spec branches (non-session-worktree mode), the iteration flow is:

1. Checkout spec branch via `CreateOrCheckoutSpecBranch()`
2. Build stage invokes Claude, which modifies files in the worktree
3. Validate stage runs tests

**On success:** Claude has committed the changes, worktree is clean, `maybeTriggerSpecMerge()` may merge back to main.

**On failure:** The orchestrator runs `runEpilogue()` (bead lifecycle, logging) then `continue`s to the next iteration. But:
- **No git cleanup step** reverts the uncommitted changes Claude made
- **No return-to-base-branch step** switches back from the spec branch
- The worktree remains dirty with Claude's uncommitted modifications

The next iteration's `ensureWorktreeClean()` precondition check (correctly) detects the dirty files and returns a `DirtyWorktreeError`, which triggers fail-fast termination of the entire run.

## Affected Code

- `internal/runner/orchestrator.go:916-943` — build failure path: runs epilogue then `continue`, no cleanup
- `internal/runner/orchestrator.go:945-987` — validation failure path: same issue
- `internal/runner/orchestrator.go:995-1030` — local gate failure path: same issue
- `internal/runner/orchestrator.go:1035-1157` — regression/review gate failures: same issue
- `internal/pipeline/epilogue/epilogue.go` — epilogue stage has no git/worktree cleanup
- `internal/runner/specbranch/git_ops.go:199-201` — the precondition check that correctly blocks checkout

## Suggested Fix

Add a post-iteration worktree cleanup step to the orchestrator's failure paths:

1. **Add a `RevertUncommittedChanges(ctx)` method** to the `specbranch.GitOps` (or a new interface) that runs `git checkout -- .` + `git clean -fd` to restore worktree cleanliness after a failed iteration.

2. **Add a `ReturnToBaseBranch(ctx)` method** that checks out the configured base branch (main) after each iteration, so the next iteration starts from a known state.

3. **Wire cleanup into all failure paths** in the orchestrator loop — after `runEpilogue()` and before `continue`, call the cleanup. Guard with `if o.cfg.GitCheckout != nil` so it only runs when spec branches are configured.

4. **Consider adding the cleanup to the epilogue stage** as an optional GitCleanup dependency, keeping the orchestrator lean. The epilogue already runs on both success and failure paths.

Alternative: Instead of reverting, stash the failed iteration's changes so they can be inspected later. But this risks stash accumulation.

## Evidence

1. **No cleanup in failure paths:** All failure branches in the orchestrator loop (build failure at :934, validation failure at :978, gate failures) run `runEpilogue()` then `continue` without any git cleanup.

2. **Epilogue has no git awareness:** The epilogue stage (`internal/pipeline/epilogue/epilogue.go`) handles bead lifecycle, status, logging, and between-iterations commands — but no git operations.

3. **Success path works:** On success, Claude commits changes (worktree clean), and `maybeTriggerSpecMerge()` handles merging back to main. The asymmetry between success and failure paths is the root cause.

4. **Correctly designed precondition:** The `ensureWorktreeClean()` check and fail-fast behavior are correct per the project rules. The bug is upstream — the worktree should never reach a dirty state between iterations.

5. **Rules require preflight gate:** The project rules state "Before build phase starts, run a hard preflight environment gate (clean worktree, queue-state writeability, spec-branch checkout viability)." A run-start preflight would catch pre-existing dirty state, but would not prevent this in-run cascading issue.
