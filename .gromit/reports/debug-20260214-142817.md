# Bug Investigation: Heartbeat/Stall Detection Disconnected + Per-Model Timeouts Not Applied

## Symptom

During `gromit run`, even after extending timeout config values, the following warning appears after 1m30s of silence:

```
Running validation commands directly...
Running Claude with model: sonnet
cmd: claude -p --model sonnet --dangerously-skip-permissions
prompt length: 45229 bytes

WARNING: No output from Claude CLI after 1m30s. Possible causes:
  - Rate limiting (API quota exhausted)
  - Authentication issue (run 'claude' manually to check)
  - Network connectivity problem
  - Claude CLI waiting for input (check stderr above)
```

The same stalling behavior (long periods with zero output) also occurs with the Codex provider, though without the warning message.

## Root Cause

Two independent bugs combine to produce this behavior:

### Bug 1: Heartbeat + stall detection is never wired into production invocations

The `startHeartbeat()` function exists in two places:
- `internal/runner/runner.go:1223` (Runner method)
- `internal/runner/execution/heartbeat.go:29` (standalone function)

**Neither is called from any production code path.** They are only exercised in tests.

The actual invocation path is:
1. `Runner.makeInvokeFn()` (runner.go:948) calls `r.executeClaudeInvocation()`
2. Which calls `r.invoker.Execute()` (execution/invoker.go:42)
3. Which calls `p.StreamRun()` directly with no heartbeat

Consequences:
- **No periodic status output** — invocations appear frozen to the user
- **No stall detection** — `stallFired` in invoker.go:70 is initialized `false` and never set to `true`
- The `stall_timeout` (180s) and `stall_timeout_active` (600s) config values are dead code
- The escalation handler's stall-based retry logic (escalation/handler.go:248) can never trigger

### Bug 2: Per-model invocation timeouts are not applied to the Claude client

At `runner.go:189` and `runner.go:237`, the Claude client is always created with the base timeout:
```go
client, cErr := claude.NewClient(def.Binary, def.Flags, cfg.Claude.Timeout)
```

This uses `cfg.Claude.Timeout` (900s), ignoring per-model overrides:
- `sonnet.timeout: 1200` — ignored
- `opus.timeout: 1800` — ignored

The `config.ClaudeConfig.TimeoutsForModel()` function (config.go:592) exists, is tested, and correctly returns per-model values. But at `process.go:40`, only the 4th return value (`beadTimeout`) is used:
```go
_, _, _, beadTimeoutSec := r.cfg.Claude.TimeoutsForModel(model)
```

The 1st return value (`invocationTimeout`) is discarded.

The startup monitor in `claude.go:349-357` derives its warning threshold from the client's fixed timeout:
```go
startupWarn := c.timeout / 10  // 900/10 = 90s = 1m30s
```

This is why the warning always says "1m30s" regardless of per-model config.

### Why Codex is affected

CodexProvider (provider/codex.go) has:
- No startup monitor (so no warning, but also no visibility)
- No heartbeat wired (same as Claude path)
- No invocation-level timeout (relies solely on bead context deadline, 1800-2400s)

A long-running Codex invocation is completely silent — no output, no heartbeat, no stall detection.

## Affected Code

### Primary (must change):
- `internal/runner/execution/invoker.go:42-132` — Execute() needs to start heartbeat and wire stall detection
- `internal/runner/runner.go:189` — Claude client creation needs per-model timeout
- `internal/runner/runner.go:237` — Same for backward-compat path
- `internal/runner/process.go:40` — Invocation timeout return value is discarded

### Supporting (already implemented, just disconnected):
- `internal/runner/execution/heartbeat.go` — StartHeartbeat exists, tested, ready to use
- `internal/config/config.go:592-613` — TimeoutsForModel exists, tested, returns correct values
- `internal/logger/stream.go:197-205` — RecordStall exists, tested
- `internal/runner/escalation/handler.go:248` — Stall-based retry logic exists

### Config (reference):
- `gromit.yaml:96-116` — Claude timeout config with per-model overrides

## Suggested Fix

### Fix 1: Wire heartbeat into Invoker.Execute()

The invoker should start a heartbeat goroutine alongside each StreamRun call. The `execution/heartbeat.go` already has the right interface — it just needs to be called. The stall callback should set `stallFired = true` and cancel the child context.

The invoker needs access to:
- `stall_timeout` and `stall_timeout_active` values (from config, per-model)
- An `io.Writer` for heartbeat output (already has `inv.output`)
- StreamStats (already created at invoker.go:43)

### Fix 2: Apply per-model invocation timeouts

Option A: Create per-model Claude clients (one per tier). This is clean but means multiple clients.

Option B: Pass the invocation timeout through the context rather than baking it into the client. The Claude client already creates a `context.WithTimeout(ctx, c.timeout)` — if the parent context already has a tighter deadline, it's respected.

Option C: Change the Claude client to accept timeout per-call rather than per-client. This is the cleanest but changes the StreamRun signature.

**Recommended: Option B** — have the invoker set a per-invocation timeout on the context based on `TimeoutsForModel()`, and reduce the Claude client's internal timeout to a large fallback value. This requires minimal changes.

### Fix 3: Wire startup monitor timeout from invocation timeout

The startup monitor in `claude.go:349-357` derives from `c.timeout`. If we adopt Option B above, the startup monitor should derive from the context deadline instead, or accept the timeout as a parameter.

## Evidence

1. **Grep for `startHeartbeat(` calls in non-test Go files**: zero results. The function is defined but never called in production.

2. **`stallFired` in invoker.go:70**: initialized `false`, never assigned `true`, forwarded to InvocationResult unchanged.

3. **`TimeoutsForModel` at process.go:40**: first 3 return values explicitly discarded with `_`.

4. **User's warning timestamp**: "1m30s" = 90s = 900/10, confirming the base timeout (900s) is used, not sonnet's 1200s.

5. **Both providers affected**: Claude shows the warning; Codex silently stalls. Common factor is the missing heartbeat in the invoker path.

6. **Config values are dead code in production**:
   - `stall_timeout: 180` — only read in test heartbeat calls
   - `stall_timeout_active: 600` — same
   - `model_timeouts.sonnet.timeout: 1200` — only `bead_timeout` from this struct is used
