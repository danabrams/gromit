# Bug Investigation: Iteration Slowdown and Token Churn

## Symptom
- Gromit iterations feel much slower than before.
- Recent runs also appear to consume far more model context/tokens.

## Root Cause
- This is a combined issue: **runtime latency increase + token churn increase**.
- Main contributors:
  - Validation-heavy iterations dominate runtime (large `go test` scopes and timeout-prone runner tests).
  - `precheck` is disabled, so fewer beads are fast-skipped.
  - Recent runs invoke high-context Codex flows much more frequently, with many runs exceeding 1M input tokens.
  - A recursive test pattern (`go test` executed from inside a test) contributes to long/fragile validation behavior in runner suites.

## Affected Code / Config
- `gromit.yaml:108` (`precheck.enabled: false`)
- `gromit.yaml:121` / `gromit.yaml:125` / `gromit.yaml:130` (broad `go test ... ./...` validation commands)
- `gromit.yaml:194` / `gromit.yaml:195` (both `atdd` and `tdd` enabled)
- `internal/runner/runner_split_final_verification_reclassified_test.go:230`
- `internal/runner/runner_split_final_verification_reclassified_test.go:240`
- `internal/runner/runner_split_final_verification_reclassified_test.go:257`
- `gromit.yaml:203` / `gromit.yaml:204` (new cap now set: `learnings.max_learning_chars: 2500`)

## Suggested Fix
1. Keep `learnings.max_learning_chars` capped (now set to 2500) and monitor token trend.
2. Re-enable `precheck` with conservative settings to recover cheap skips.
3. Narrow fast validation commands (changed packages / targeted scopes), keep full gate at controlled checkpoints.
4. Gate or refactor recursive runner split verification tests so they do not run in normal fast iteration loops.
5. Choose one methodology (`atdd` or `tdd`) for default runs to reduce prompt/context overhead.
6. Enforce decomposition earlier for broad beads to prevent 1M+ token invocations.
