# Bug Investigation: Refactor phase fails repeatedly for already-implemented bead

## Symptom

Bead `gromit-axqrj` ("Define Stage interface, Input/Output, and Decision types") failed 3 times
with `"error":"refactor phase failed"`. The Stage interface was already implemented in commit
`6b73e828` (file: `internal/pipeline/stage.go`). The stream log shows only ONE invocation per
iteration - the `SESSION: initialized` event (which marks a new Claude session) appears
immediately after `INVOCATION_END`, indicating the refactor phase is failing inside the single
RED invocation callback, not generating its own separate session.

## Root Cause

The failure path is:

1. `fresh_context_per_cycle: true` is set in `gromit.yaml:238`.
2. `prepareMethodologyForBead` (`process_methodology.go:54-56`) detects `FreshContextPerCycle`
   and calls `runTDDFreshContextCycles`, returning `done=true` immediately after. The main runner
   (`runner.go:299-302`) therefore returns without ever calling `executeBuildAndMethodologyLoop`.
3. `runTDDFreshContextCycles` (`process_methodology.go:90-139`) calls
   `r.tddOrchestrator.RunCycles(ctx, bc, coverageTracker, coverageCriteria)`.
4. The `tddOrchestrator.runCyclesFn` is built in `callbacks_tdd.go:39-221`. It creates a
   `tdd.CycleOrchestrator` and calls `orch.RunCycles(ctx, bc, state)`.
5. In `orchestrator.go:102-108`, `runOneCycle` is called. The RED phase invokes Claude
   (`runPhaseInvocation`, line 172), which writes test files.
6. After the RED invocation, `validateFn` is called (line 177). Because the Stage interface is
   already implemented in commit `6b73e828`, the tests pass immediately: `passed == true`
   (line 181).
7. Since `passed == true` after the RED phase, `runRefactorAndFinalValidation` is called
   (orchestrator.go:183).
8. `runRefactorAndFinalValidation` calls `executeRefactorPhase` (orchestrator.go:238).
9. `executeRefactorPhase` calls `o.runRefactorFn(ctx, bc)` (line 250).
10. `runRefactorFn` is the closure at `callbacks_tdd.go:168-176`:
    ```go
    RunRefactorFn: func(ctx context.Context, bc *runtypes.BeadContext) error {
        result := r.methodologyExec.RunRefactorPhaseWithResult(ctx, bc)
        if !result.Successful {
            return fmt.Errorf("refactor phase failed: %s", result.Reason)
        }
        return nil
    },
    ```
11. `RunRefactorPhaseWithResult` (`refactor.go:193`) calls `e.getDiffFn(bc.StartCommit)`.
    `bc.StartCommit` was captured at `setupBeadContext` (`process.go:59`) as the git HEAD
    BEFORE the bead began. Because the RED invocation wrote test files, the diff from
    `bc.StartCommit` is non-empty, so the "no changes to refactor" skip guard (`refactor.go:205-208`)
    does NOT fire.
12. `RunRefactorPhaseWithResult` proceeds to call `e.refactorInvokeFn` - which calls
    `r.runRefactorWithRouter` (`process.go:288`). This is the ONE invocation the stream log shows.
13. The refactor invocation fails (likely because the stage is already complete - Claude has nothing
    useful to refactor), returning `Successful: false, Reason: "invoke_unsuccessful"` or
    `"invoke_failed"`.
14. The error propagates back: `runRefactorFn` returns an error, `executeRefactorPhase` returns
    `refactorOutcomeFailed` (orchestrator.go:251-252), `runRefactorAndFinalValidation` returns
    `fmt.Errorf("refactor phase failed")` (orchestrator.go:233-234), and the iteration fails.

**The bug**: When the RED phase finds tests already pass (because the Stage interface is already
implemented), the system correctly skips the GREEN phase. However, it still triggers the refactor
path, which runs a Claude invocation over a diff that represents only the test files written in the
RED phase. This refactor invocation fails because there is nothing meaningful to refactor - the
implementation already exists, was committed before this bead ran, and the only new changes are
the RED test files. The refactor then fails, causing the whole iteration to be reported as failed.

## Affected Code

- `internal/runner/tdd/orchestrator.go:181-189` — the `passed == true` early-exit path in
  `runOneCycle` that calls `runRefactorAndFinalValidation` when RED validation passes
- `internal/runner/tdd/orchestrator.go:227-235` — `runRefactorAndFinalValidation` which returns
  error on `refactorOutcomeFailed`
- `internal/runner/tdd/orchestrator.go:238-270` — `executeRefactorPhase` which calls `runRefactorFn`
- `internal/runner/callbacks_tdd.go:168-176` — `RunRefactorFn` closure that calls
  `r.methodologyExec.RunRefactorPhaseWithResult(ctx, bc)`
- `internal/runner/methodology/refactor.go:193-285` — `RunRefactorPhaseWithResult` which checks
  `getDiffFn(bc.StartCommit)` but uses the bead's start commit (pre-RED), not the post-RED HEAD
- `internal/runner/process_methodology.go:54-56` — where `FreshContextPerCycle` routes to
  `runTDDFreshContextCycles` and returns `done=true`

## No Double-Refactor Bug

The suspected double-refactor (question 5) does NOT occur. When `FreshContextPerCycle` is true,
`prepareMethodologyForBead` returns `done=true` at `process_methodology.go:56`, and
`processBeadWithContext` (`runner.go:299-302`) immediately returns `bc, bc.Result` without
reaching `runMethodologyExecution`. The `executeBuildAndMethodologyLoop` path (which contains the
`tddActive` refactor call at `process_methodology.go:582-590`) is never entered in the
fresh-context path. There is no double-refactor.

## SESSION: initialized

`SESSION: initialized` is logged by `logger/stream.go:336`:
```go
case "system":
    sl.LogEvent("SESSION: initialized (subtype=%s)", event.Subtype)
```
This fires when Claude emits a `{"type": "system"}` JSON stream event, which marks the START
of a new Claude invocation session (CLI startup). Seeing it immediately after `INVOCATION_END`
confirms each refactor attempt is a single session: the RED invocation starts a session, and
the refactor (being the same RED invocation at the `RunRefactorFn` callback level, not a
separate stream session) then fails before any new session initializes. The "one invocation per
iteration" observation is thus explained: the refactor fails inside `RunRefactorPhaseWithResult`
after the invocation succeeds but the invocation result is unsuccessful, not before the invocation.

## Suggested Fix

**Option A (cleanest)**: In `orchestrator.go:runOneCycle`, when `passed == true` after the RED
phase (tests already pass), check whether any implementation files were actually changed since
`bc.StartCommit` vs only test files were changed. If only test files were written (typical when
the implementation pre-exists), skip the refactor phase and mark as done directly.

**Option B**: In the `RunRefactorFn` callback (`callbacks_tdd.go:168-176`), capture a
post-RED-invocation commit HEAD before calling `RunRefactorPhaseWithResult`, and pass a
diff-from-post-RED-HEAD to detect whether there are any implementation changes to refactor.
If the only diff from post-RED-HEAD to HEAD is test files, skip refactor.

**Option C (pragmatic)**: In `orchestrator.go:runRefactorAndFinalValidation`, when the
immediately-preceding trigger was a `passed==true` RED validation (not a completed GREEN phase),
skip the refactor phase entirely since no implementation was written in the current cycle.

**Option D (immediate workaround)**: Close the bead manually using `bd close` since the
implementation already exists. This is the correct action for `gromit-axqrj`.

## Evidence

1. `gromit.yaml:238`: `fresh_context_per_cycle: true` - confirms the TDD orchestrator path.
2. `gromit.yaml:229`: `tdd: true` - TDD is globally enabled.
3. `internal/pipeline/stage.go` exists from commit `6b73e828` - Stage interface already
   implemented before this bead ran.
4. `orchestrator.go:181-189`: `passed==true` after RED immediately triggers
   `runRefactorAndFinalValidation` with no guard against "already done" state.
5. `refactor.go:200`: `e.getDiffFn(bc.StartCommit)` uses the bead's original start commit;
   the diff includes RED-written test files, so `diff == ""` check does not fire.
6. `callbacks_tdd.go:191-196`: `GetDiffFn` in the TDD orchestrator also uses
   `activeBC.StartCommit` (same start commit), confirming the diff-from-start reflects
   the RED test files written.
7. Stream log pattern: ONE `SESSION: initialized` + ONE `INVOCATION_END` per iteration confirms
   the refactor Claude call fires but returns failure (no successful result event, no additional
   SESSION:initialized for a second invocation).
8. `process_methodology.go:54-56` + `runner.go:299-302`: confirms no double-refactor -
   `done=true` exits before `executeBuildAndMethodologyLoop`.
