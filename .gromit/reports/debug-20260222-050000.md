# Bug Investigation: TDD fresh-context cycles run as single broad cycle

## Symptom
When running `gromit run --spec runner-pipeline -n 1`, bead gromit-5x41e ("Create OrchestratorTestHelper with dependency injection for acceptance tests") produced a single RED commit with ALL tests and a single GREEN commit with ALL implementation, instead of incremental one-test-at-a-time TDD cycles.

User observed in terminal output:
```
cmd: claude -p --model sonnet ...
prompt length: 2472 bytes
Let me implement TDD cycles. I'll create the test file first (Cycle 1 RED):
...
Now write the implementation (GREEN for all 4 cycles):
All tests pass.
```

## Root Cause
The fresh-context TDD orchestrator IS running (confirmed: `fresh_context_per_cycle: true` in config, code path is activated). But the orchestrator only runs **one cycle** because the bead has empty `ExpectedOutputs`.

**Chain of causation:**

1. Bead `gromit-5x41e` has `expected_outputs: []` (confirmed via `bd show --json`)
2. `tddExpectedOutputsOrTitle()` (`process_methodology.go:226-238`) falls back to the full bead title: "Create OrchestratorTestHelper with dependency injection for acceptance tests"
3. `resolveInitialCycleState()` (`callbacks_tdd.go:265-283`) creates `Remaining: ["Create OrchestratorTestHelper..."]` — a single entry
4. The orchestrator (`tdd/orchestrator.go:108-115`) runs cycles while `!state.IsComplete()` — but with only one Remaining item, it runs exactly one RED→GREEN→REFACTOR cycle
5. In that single cycle, `AssembleRedHandoff` passes the entire title as `SpecExcerpt` — Claude's RED phase writes tests for ALL 4 deliverables because the spec encompasses everything
6. The GREEN phase receives all failing tests and writes all implementation at once

**The architecture is correct; the data is wrong.** The decomposition phase creates beads with rich descriptions listing individual deliverables but does NOT populate `expected_outputs` with those deliverables.

## Affected Code
- `internal/runner/process_methodology.go:80-88` — title fallback when `ExpectedOutputs` empty
- `internal/runner/callbacks_tdd.go:219-226` — initial cycle state from `ExpectedOutputs`
- `internal/runner/callbacks_tdd.go:265-283` — `resolveInitialCycleState` creates broad single-item Remaining
- `internal/runner/tdd/orchestrator.go:108-115` — `RunCycles` loop (works correctly)
- `internal/runner/tdd/assembly.go` — `AssembleRedHandoff` passes the single broad spec excerpt

## Suggested Fix

**Option A: Extract requirements from bead description at TDD time**
Add a pre-processing step in `runTDDFreshContextCycles` that parses the bead description to extract individual deliverables when `ExpectedOutputs` is empty. The description already uses patterns like "Includes: X, Y, Z" that can be parsed.

**Option B: Populate `expected_outputs` during decomposition**
Update the decomposition phase to extract deliverables from the bead description and set them as `expected_outputs`. This is upstream of the TDD system and would benefit other methodology consumers too.

**Option C: Use Claude to extract requirements (LLM-based)**
Before the first RED cycle, invoke a lightweight Claude call (haiku) to parse the bead title+description into discrete testable requirements. This handles arbitrary description formats.

**Recommended: Option A or B** — Option A is local to the TDD path and can be done without changing the decomposition pipeline. Option B is more correct architecturally but has wider blast radius.
