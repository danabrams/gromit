# Bug Investigation: Stale worktree blocks spec branch checkout

## Symptom
Bead "Add SetItems and Render to ListModel with tests (gromit-r9afc)" fails with:
```
branch checkout failed for gromit/spec-tui-pipeline-view: failed to create or checkout spec branch gromit/spec-tui-pipeline-view:
  create attempt failed: exit status 128 (stderr: fatal: a branch named 'gromit/spec-tui-pipeline-view' already exists);
  checkout attempt failed: exit status 128 (stderr: fatal: 'gromit/spec-tui-pipeline-view' is already used by worktree at '/Users/dabrams/gromit-gromit-run-1772591657584751000')
```

## Root Cause
Two related issues:

### 1. Stale session worktrees not cleaned up
Session worktrees from previous `gromit run` invocations persist after the run completes or fails. The worktree at `/Users/dabrams/gromit-gromit-run-1772591657584751000` holds branch `gromit/spec-tui-pipeline-view`, preventing any other worktree or the main repo from checking it out.

At time of investigation, 4 stale session worktrees exist:
- `/Users/dabrams/gromit-gromit-run-1772582626480280000` (detached HEAD)
- `/Users/dabrams/gromit-gromit-run-1772584253396131000` (detached HEAD)
- `/Users/dabrams/gromit-gromit-run-1772591657584751000` [gromit/spec-tui-pipeline-view]
- `/Users/dabrams/gromit-gromit-run-1772611271646770000` [gromit/spec-validation-auto-fix-integration]

### 2. No worktree-conflict recovery in CreateOrCheckoutSpecBranch
`internal/runner/specbranch/git_ops.go:109-155` handles "branch already exists" by falling back to plain checkout, but doesn't handle "branch already used by worktree". When git reports the worktree conflict, the function just returns an error with no recovery attempt.

## Affected Code
- `internal/runner/specbranch/git_ops.go:109-155` — `CreateOrCheckoutSpecBranch()` lacks worktree-conflict detection/recovery
- `internal/worktree/worktree.go:337-352` — `Cleanup()` exists but isn't called reliably on run exit
- `internal/runner/orchestrator.go:601` — calls `CreateOrCheckoutSpecBranch` and marks bead as failed on error

## Suggested Fix
Two-part fix:

**Part A: Worktree-conflict recovery in CreateOrCheckoutSpecBranch**
When checkout fails with "already used by worktree", detect this pattern and:
1. Check if the conflicting worktree's process is still alive (parse PID from worktree path pattern `gromit-run-<timestamp>`)
2. If the process is dead, remove the stale worktree via `git worktree remove --force <path>`
3. Retry the checkout

**Part B: Proactive stale worktree cleanup**
Add a cleanup step at the start of `gromit run` that prunes stale session worktrees:
1. List all worktrees matching the session pattern (`*-gromit-run-*`)
2. For each, check if the owning process is alive
3. Remove dead worktrees before starting the run

## Evidence
- `git worktree list` shows 4 stale session worktrees with no active processes
- Error message explicitly identifies the worktree conflict: `'gromit/spec-tui-pipeline-view' is already used by worktree at '/Users/dabrams/gromit-gromit-run-1772591657584751000'`
- `internal/worktree/worktree.go` has `Cleanup()` and `RemoveByPath()` methods that could be leveraged
- The `procutil` package already has `IsProcessAlive()` for liveness checks
