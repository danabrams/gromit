# Bug Investigation: Scope gate blocks gromit-cr50o (12 expected outputs, max 5)

## Symptom
Bead `gromit-cr50o` ("Restore formatting functions to format.go") is blocked by the scope gate with message: "Scope gate: bead gromit-cr50o has 12 expected outputs (max 5), blocking". This prevents the bead from being built and also blocks downstream bead `gromit-jetjq`.

## Root Cause
Two issues identified:

### Immediate: Bead too broadly scoped
The bead has 12 acceptance criteria lines. Since `ExpectedOutputs` was not explicitly set, `resolveExpectedOutputsFromAcceptanceCriteria()` (bead.go:88-100) maps each acceptance criteria line to an expected output, resulting in 12 expected outputs. The scope gate in `gate.go:113-122` blocks beads exceeding `maxScopeFiles = 5`.

### Structural: Scope gate blocks but doesn't auto-decompose
The scope gate returns `pipeline.Block` when file count exceeds the threshold. The Gate already has a `Decomposer` interface and `WithDecomposer()` method used for proactive keyword-based decomposition (gate.go:124-134), but the scope gate path (gate.go:113-122) doesn't attempt decomposition. Additionally, the Decomposer is not wired in `constructor.go:96-98`.

## Affected Code
- `internal/pipeline/prepare/gate.go:113-122` - Scope gate returns Block without attempting decomposition
- `internal/bead/bead.go:88-100` - `resolveExpectedOutputsFromAcceptanceCriteria()` maps criteria to expected outputs
- `internal/runner/constructor.go:96-98` - Gate constructed without Decomposer

## Resolution

### Short-term: Manual decomposition (applied)
Decomposed `gromit-cr50o` into 3 sub-beads with <=5 acceptance criteria each:
- `gromit-cr50o.1`: Run display formatting (formatRunningLine, formatEscalationBreakdown, formatRecurrenceBreakdown, update formatRun) - 5 criteria
- `gromit-cr50o.2`: Health, recommendation, and model performance formatting - 4 criteria
- `gromit-cr50o.3`: SPC formatting functions and constants - 5 criteria

Parent `gromit-cr50o` closed. All 3 children block `gromit-jetjq`.

### Long-term: Auto-decompose on scope failure
Created `gromit-nwhgo` (P2 feature): Modify the scope gate to attempt decomposition before blocking. The Decomposer interface already exists; the scope gate path just needs to call it (similar to the proactive decomposition path at gate.go:126-132).

## Evidence
- Scope gate constant: `maxScopeFiles = 5` (gate.go:15)
- Bead acceptance criteria: 12 newline-separated lines
- Resolution function: `resolveExpectedOutputsFromAcceptanceCriteria()` parses criteria into expected outputs when ExpectedOutputs is empty
- Proactive decomposition path exists (gate.go:124-134) but scope gate path (gate.go:113-122) doesn't use it
- Decomposer not wired in constructor.go
