# Bug Investigation: gromit-yfj6 fails prelaunch and leaves stale running state

## Symptom
`gromit-yfj6` failed immediately in iteration 1 with:
`branch checkout failed for main: failed to create or checkout spec branch main: exit status 1`

Observed run artifacts:
- `.gromit/logs/events-20260302-131507.jsonl` shows `bead_failed`, `epilogue_complete`, `iteration_complete`, then `Gromit loop complete`.
- `.gromit/logs/run-20260302-131507.jsonl` contains a single prelaunch failure row with `duration_ms=0`, `cost_usd=0`, `input_tokens=0`, `output_tokens=0`.
- `.gromit/status.json` remained `running: true` with dead PID `283122`.

## Root Cause
There are two coupled issues:

1. Bead failure path (`why this bead failed`)
- `gromit-yfj6` has no `spec:<name>` label (`from-review`, `tech-debt` only).
- `specbranch.Router.BranchForLabels(...)` therefore returns the base branch (`main`) for non-spec beads.
- Orchestrator prelaunch branch checkout always runs when `BranchRouter`/`GitCheckout` are configured.
- `specbranch.GitOps.CreateOrCheckoutSpecBranch(...)` attempts `git checkout -b main`, then `git checkout main`; second checkout failed with exit status 1.
- Error details from git stderr are dropped in this path, so exact git cause is hidden in runtime logs.

2. No retry / no clean-exit status (`why it did not retry or exit cleanly`)
- Retry: branch-checkout failures are treated as prelaunch iteration failures and are not passed through build/escalation retry logic.
- Loop termination: after that failed iteration, the same bead was re-offered; skip-tracker interpreted this as “all processed beads re-offered” and exited loop intentionally.
- Clean exit signaling bug: after loop exit, `Orchestrator.Run()` calls `assertEfficiencyCompleteness(...)`. The only row had zero cost/tokens, so completeness check fails and `Run()` returns error before emitting `RunCompleteEvent` and before marking `clean_exit=true`.
- Status lifecycle gap: `status.json` is written with `running=true` at iteration start, but there is no guaranteed final `running=false` write on run errors; stale status remains until explicit status cleanup logic runs.

## Affected Code
- `internal/runner/orchestrator.go`
  - Branch checkout prelaunch failure handling (around line ~446)
  - Skip/re-offer early-exit behavior (around line ~362)
  - Post-loop completeness assertion before `RunCompleteEvent` (around lines ~812-836)
- `internal/runner/specbranch/router.go`
  - Non-spec label routing defaults to base branch (`main`) (around `BranchForLabels`)
- `internal/runner/specbranch/git_ops.go`
  - `CreateOrCheckoutSpecBranch` drops git output context in wrapped error
- `internal/logger/efficiency.go`
  - `AssertEfficiencyCompleteness` treats all zero cost/tokens rows as incomplete without failure-phase exception
- `internal/runner/status.go`
  - `WriteFinal` exists but is not wired into run lifecycle on all exits

## Suggested Fix
1. Make non-spec branch routing safe in session worktrees:
- Either skip checkout entirely for non-spec beads (preferred), or only checkout when target branch differs and checkout is valid for current worktree mode.

2. Preserve git stderr in branch checkout errors:
- Include command output in `CreateOrCheckoutSpecBranch` error to make root cause diagnosable.

3. Fix end-of-run lifecycle on error exits:
- Guarantee final run completion semantics (event + state/status finalization) even when post-loop assertions fail.
- Ensure `status.json` is finalized with `running=false` on all `Run()` return paths.

4. Align efficiency completeness with prelaunch sentinel semantics:
- Do not treat invocation/prelaunch sentinel rows as generic “missing efficiency data,” or gate this check behind iteration classes where efficiency fields are expected.
