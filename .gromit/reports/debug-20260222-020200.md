# Bug Investigation: gromit run appears stuck at startup

## Symptom

`gromit run --spec runner-pipeline` (PID 861717, started at 01:59) appears to hang at startup with no output, no log file created, and no status.json updates. The user observes a completely silent process that looks stuck.

## Root Cause

The process is **not stuck**. It has spawned a Claude CLI child process (PID 861747: `claude -p --model sonnet --dangerously-skip-permissions`) and is actively processing a bead. Two bugs in the Runner-to-Orchestrator refactoring cause the "stuck" appearance:

### Bug 1: Spec label filtering silently discarded (correctness)

In `cmd/gromit/main.go:196-197`, the `--spec` flag is resolved but never passed to the Orchestrator:

```go
// Note: dryRun and label filters are not yet supported by the new Orchestrator API
_ = labels
_ = dryRun
```

`GetBead()` in `constructor.go:354-356` calls `beadsClient.Ready()` without any label filtering, so the Orchestrator processes ANY ready bead regardless of the `--spec` flag. This means `--spec runner-pipeline` is silently ignored.

### Bug 2: All observability infrastructure missing (UX)

The new `Orchestrator.Run()` (`orchestrator.go:77`) is a thin stage-sequencing loop that lacks the observability infrastructure from the old `Runner.Run()`:

1. **No stream log file** — `Runner.Run()` created a stream logger at line 263-270; Orchestrator has no equivalent
2. **No status.json updates** — `statusWriterAdapter.Write()` at `constructor.go:211-213` is a no-op placeholder:
   ```go
   func (a *statusWriterAdapter) Write(iteration int, beadID, beadTitle string) error {
       // Status writing logic placeholder - would typically write to a status file
       return nil
   }
   ```
3. **No console progress messages** — No "Starting iteration...", "Streaming to:", or any iteration feedback
4. **No iteration JSONL logging** — The Orchestrator doesn't write per-iteration entries to `run-*.jsonl`

## Affected Code

- `cmd/gromit/main.go:192-199` — runLoop discards labels and dryRun
- `internal/runner/constructor.go:354-356` — GetBead has no label filter
- `internal/runner/constructor.go:206-214` — statusWriterAdapter is no-op
- `internal/runner/orchestrator.go:77-166` — Run() lacks logging/status/progress infrastructure
- `internal/runner/orchestrator.go:86-160` — main loop has no per-iteration console output

## Suggested Fix

### Priority 1: Wire spec label filtering into GetBead (correctness fix)

The `GetBead` closure needs to accept and apply label filters. Options:
- Pass labels into `newRunnerImpl()` and filter in the `getBeadFn` closure
- Add a `WithLabels()` option to OrchestratorConfig
- Use `beadsClient.ReadyWithLabels()` if the bead client supports it

### Priority 2: Replace no-op statusWriterAdapter (quick win)

Wire the real `StatusWriter` from `internal/runner/` into the epilogue stage instead of the placeholder.

### Priority 3: Add stream logging and console progress (observability)

Either:
- Add a pre-loop setup and per-iteration logging to `Orchestrator.Run()`
- Create a logging decorator/middleware that wraps stage execution
- Move the stream logger and progress output into the Epilogue stage

### Priority 4: Restore iteration JSONL logging

Wire the iteration logger into the Orchestrator so per-iteration entries are written to `run-*.jsonl`.

## Evidence

1. **Process tree** confirms active execution:
   ```
   gromit(861717)---claude(861747) [26 threads, 25s CPU]
   ```

2. **No log file for current run** — latest is `run-20260222-002826.jsonl` (previous run at 00:28)

3. **status.json stale** — shows PID 792467 (previous run), `running: false`

4. **Thread analysis** — Thread 861719 is in `do_wait` (waiting for claude child process), others in `futex_wait_queue` (Go runtime parking). Normal execution pattern.

5. **Bead mismatch** — `bd ready` returns `gromit-121lh` first (unrelated to runner-pipeline spec), confirming spec filtering is not applied

6. **Previous runs** of `gromit-igprl.2` in logs show repeated timeouts, suggesting the bead itself may also have issues, but the "stuck at startup" symptom is purely observability.
