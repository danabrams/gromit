# Bug Investigation: Validation failures do not trigger fix attempts before iteration exits

## Symptom
Validation failures currently end the iteration immediately. The system does not attempt auto-fix (`gofmt`/`goimports`) or Claude-based validation recovery before moving on.

Observed behavior aligns with the user report: when validation fails, the run continues to the next offered bead/iteration path instead of trying to repair test failures first.

## Root Cause
Stage 3 in the orchestrator is wired to `internal/pipeline/validate.Validate`, which is a fail-fast command runner. On first failing validation command it returns `pipeline.Block` and the orchestrator immediately emits failure, runs epilogue on the failure path, and `continue`s.

A separate recovery-capable implementation already exists in `internal/runner/validation.Runner` (`RunWithRecovery*`) and explicitly supports:
- trivial auto-fix first
- Claude fix attempts after auto-fix
- retry gating via `Validation.MaxValidationRetries`

That recovery runner is not used in the Stage 3 orchestration path.

Additional impact: each bead is marked `processedBeads[b.ID] = true` before validation. After a validation failure, this means the same bead will not be retried in the same run even if re-offered by `bd`, reinforcing the "moves on without fixing" symptom.

## Affected Code
- `internal/runner/orchestrator.go:335` (processed-bead single-pass behavior)
- `internal/runner/orchestrator.go:561` (Stage 3 validate invocation)
- `internal/runner/orchestrator.go:562` (fail-fast branch on validation failure)
- `internal/pipeline/validate/validate.go:45` (validate stage implementation)
- `internal/pipeline/validate/validate.go:127` (returns block on first non-zero exit)
- `internal/runner/validation/runner.go:111` (existing recovery-capable flow)
- `internal/runner/validation/runner.go:133` (recovery loop implementation)
- `internal/config/config_defaults.go:121` (`MaxValidationRetries` default set, but ineffective in Stage 3)

## Suggested Fix
Replace or extend Stage 3 wiring so validation uses `validation.Runner.RunWithRecoveryForCommandsWithEscalation(...)` (or equivalent adapter) instead of the current fail-fast `pipeline/validate` implementation.

Design target:
- Preserve existing Stage 3 event semantics (`ValidationStart/Pass/Fail`)
- Attempt direct validation first
- On `ErrValidationFailed`, run recovery path (auto-fix then Claude fix)
- Respect phase deadline and command timeout behavior
- Populate iteration result fields consistently (`Validated`, `ValidationMode`, `ValidationRetried`, `TrivialAutoFixed`, failure summaries)
- Keep failure path behavior unchanged only after recovery is exhausted

## Evidence
- `internal/runner/orchestrator.go:561-597` calls `o.cfg.Validate.Run(...)` and exits iteration on non-proceed.
- `internal/pipeline/validate/validate.go:108-136` blocks on first non-zero validation command, no recovery hook.
- `internal/runner/validation/runner.go:111-201` contains explicit recovery logic (auto-fix + Claude + bounded retries).
- `internal/config/config_defaults.go:121-123` sets `MaxValidationRetries = 2`, indicating expected retry behavior exists in config surface.
- `internal/runner/orchestrator.go:335-350` marks beads processed before validation, preventing same-run retry after failure.
