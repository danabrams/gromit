# Bug Investigation: Missing cost tracking for Codex models and Haiku

## Symptom

`gromit status` shows $0.00 cost for all Codex models (gpt-5.2-codex, gpt-5.3-codex) and Haiku, despite significant token usage. Only Opus and Sonnet display non-zero costs. Aggregated data from recent logs confirms:

```
gpt-5.2-codex    iters=42  total_cost=$    0.00  total_tokens=117,806,832
gpt-5.3-codex    iters= 7  total_cost=$    0.00  total_tokens= 14,981,504
haiku             iters= 2  total_cost=$    0.00  total_tokens=          0
opus              iters= 4  total_cost=$   11.12  total_tokens=     39,151
sonnet            iters=31  total_cost=$   41.73  total_tokens=    207,861
```

Codex models report tokens but zero cost. Haiku reports neither.

## Root Cause

**Two distinct bugs, one shared gap:**

### Bug 1: Codex CLI doesn't report `total_cost_usd` in JSONL events

The Codex CLI's `turn.completed` events include `input_tokens` and `output_tokens` but `total_cost_usd` is always 0. The fallback cost estimation in `estimatedCostUSD` (callbacks.go:110-120) should handle this by looking up per-1k-token pricing from the provider config. However, it fails due to Bug 2.

### Bug 2: Provider name mismatch breaks config-based cost estimation

`estimatedCostUSD` looks up pricing via `r.cfg.Providers[providerName]`. The `providerName` comes from `p.Name()` which returns the hardcoded runtime name:
- `ClaudeProvider.Name()` returns `"claude"` (codex.go:54 / claude.go:43)
- `CodexProvider.Name()` returns `"codex"`

But in gromit.yaml, the config key for the Codex provider is `"openai"`:

```yaml
providers:
  claude:    # config key matches runtime name ✓
    binary: claude
    ...
  openai:    # config key "openai" ≠ runtime name "codex" ✗
    binary: codex
    ...
```

So `r.cfg.Providers["codex"]` returns nothing — the lookup silently fails, and `estimatedCostUSD` returns 0.

### Bug 3: Pricing values commented out in gromit.yaml

Even if the name lookup were fixed, cost estimation would still return 0 because `cost_per_1k_input` and `cost_per_1k_output` are commented out for both providers:

```yaml
providers:
  claude:
    # cost_per_1k_input: 0.015    ← commented out
    # cost_per_1k_output: 0.075   ← commented out
  openai:
    # cost_per_1k_input: 0.005    ← commented out
    # cost_per_1k_output: 0.015   ← commented out
```

`ProviderDef.EstimateCost()` (config.go:305-313) returns 0 when both pricing fields are 0.

### Haiku: Not a tracking bug

Haiku's 2 iterations in recent logs were all `outcome: scope_blocked` — the scope checker blocked them before any LLM invocation, so 0 cost and 0 tokens is correct. Haiku cost tracking through `ClaudeProvider.StreamRun` should work because `processStreamJSONWithCost` parses cost from `result` events regardless of handler presence. Claude CLI does report `total_cost_usd` for haiku. The user's observation is accurate but the root cause is that haiku rarely runs builds (P2 beads are uncommon), and when it does, the Claude provider's direct cost reporting handles it.

## Affected Code

- `internal/runner/callbacks.go:110-120` — `estimatedCostUSD()` provider name lookup
- `internal/runner/constructor.go:192-217` — `buildProvidersFromConfig()` where config keys diverge from runtime names
- `gromit.yaml:29-30, 41-42` — commented-out pricing fields
- `internal/config/config.go:299-313` — `ProviderDef.EstimateCost()` (working correctly, just never reached)

## Suggested Fix

**Three changes, all required:**

1. **Fix the provider name → config lookup** (callbacks.go): When `r.cfg.Providers[providerName]` fails, iterate over all ProviderDef entries and match by `def.Binary` containing the provider name (e.g., binary "codex" matches runtime name "codex"). Better approach: build a `providerCostDefs map[string]config.ProviderDef` at runner construction time, keyed by `p.Name()` instead of config key.

2. **Uncomment and set pricing in gromit.yaml**: Enable `cost_per_1k_input` and `cost_per_1k_output` for both providers with current pricing. For Codex models, verify current per-1k-token rates.

3. **Populate the provider field in iteration logs**: The `provider` field in IterationLog entries is currently empty (`omitempty` hides it). Ensure `bc.Result.Provider` is set before writing the log entry so cost analysis can distinguish providers.

## Evidence

**Raw JSONL entries showing the problem:**
```json
// Codex: tokens present, cost zero
{"model":"gpt-5.2-codex","cost_usd":0,"input_tokens":420938,"output_tokens":4576}

// Claude sonnet: cost present from stream result event
{"model":"sonnet","cost_usd":0.8732,"input_tokens":26,"output_tokens":5454}

// Haiku: scope_blocked, never invoked
{"model":"haiku","cost_usd":0,"input_tokens":0,"output_tokens":0,"outcome":"scope_blocked"}
```

**Code trace confirming name mismatch:**
- `invoker.go:202`: `ProviderName: p.Name()` → sets "codex"
- `callbacks.go:81`: `r.estimatedCostUSD("codex", 0, 420938, 4576)`
- `callbacks.go:115`: `r.cfg.Providers["codex"]` → not found (config key is "openai")
- Returns 0

**Cost magnitude**: At typical Codex pricing (~$0.003/1k input, ~$0.012/1k output), the 42 gpt-5.2-codex iterations represent approximately $354 in input tokens + $17 in output tokens = ~$371 in untracked spend. This is the invisible cost the user is concerned about.
