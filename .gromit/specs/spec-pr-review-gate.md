# Spec PR Review Gate

## Specification

When all beads for a spec complete, create a GitHub pull request as the completion mechanism — with CI-driven validation, iterative LLM review with automated fixes, and human approval before merge. The run loop continues processing other beads while PRs await approval.

This spec subsumes and completes the wiring gaps in spec-branch-merge-pipeline. It covers both the branch-per-spec routing (partially built, not connected) and the PR-based merge gate (new).

### Part 1: Branch-Per-Spec Wiring (Complete Existing Infrastructure)

The specbranch and specmerge packages are built but not connected to the run loop. This spec completes the wiring:

**Branch checkout before bead execution.** Add a `Router` field to `Orchestrator`. Between Gate (Proceed) and Build, call `Router.BranchForLabels(bead.Labels)` to resolve the target branch. If the bead has a `spec:<name>` label, call `GitOps.CreateOrCheckoutSpecBranch()` to switch to `gromit/spec-<name>` before Build runs. Non-spec beads stay on main.

**SpecMergeController injection.** Wire `specmerge.Pipeline` into `OrchestratorConfig.SpecMergeController` in constructor.go. Currently the field is declared but never set, causing `maybeTriggerSpecMerge()` to no-op.

**Trigger() implementation.** Replace the stub in `specmerge/pipeline.go` with the actual pipeline logic: push branch, create PR, initiate review cycle (see Part 2).

**Branch restoration after spec beads.** After a spec bead completes and the next bead is non-spec (or a different spec), the orchestrator must checkout the correct branch for the next bead. The Router + GitOps calls handle this naturally — each iteration resolves and checks out the right branch.

### Part 2: PR Creation

When the last bead of a spec closes, `maybeTriggerSpecMerge()` fires and the pipeline:

1. Pushes the `gromit/spec-<name>` branch to origin.
2. Creates a GitHub PR via `gh pr create` targeting main.
3. Sets the PR title to the spec name (human-readable).
4. Generates a comprehensive PR body (see PR Summary below).
5. Records the PR number in spec state for subsequent polling.

The run loop does not block. It continues processing other beads (non-spec or other specs). Between iterations, it polls open spec PRs for status changes (CI completion, review findings, human approval, merge).

### PR Summary

The PR body is a structured, legible summary designed for human review. It includes:

- **Spec objective** — what the spec set out to accomplish, pulled from the spec document.
- **What changed** — a high-level narrative of the implementation approach, not a file list. Describes the key design decisions and how the pieces fit together.
- **Acceptance criteria status** — each criterion from the spec with a pass/fail indicator and brief evidence (test name, behavior observed).
- **Files changed** — grouped by package/concern, with one-line descriptions of what changed in each.
- **Test coverage** — summary of new/modified tests, what they verify, and any acceptance tests included.
- **Known limitations** — anything the implementation does not cover, deferred items, or edge cases noted during review.

The summary is generated by an LLM call with the full diff and spec document as context. It must be factual (grounded in the actual diff), not aspirational.

### CI Validation

Once the PR is created, CI runs the full test suite on the PR branch. This includes:

- Unit tests (`go test ./...`)
- Acceptance tests (`go test -tags acceptance ./...`)
- Contract tests (`test/contracts/`)
- Integration tests (if configured)
- `go vet ./...`
- `go build ./...`
- Any configured `full_commands` from gromit.yaml

CI failures are treated as review findings. The pipeline reads CI status via `gh pr checks` and feeds failures into the fix loop.

### LLM Review

After CI passes, the pipeline posts LLM review findings as PR review comments via `gh api` or `gh pr review`. Three review passes run in order, each a hard gate:

1. **Spec Conformance** — Does the implementation satisfy every acceptance criterion in the spec? Posted as a PR review with per-criterion findings.
2. **Code Quality** — Style, error handling, test quality, nil safety, naming. Posted as inline PR comments on specific lines where possible.
3. **Architectural Review** — Module sizing, boundary seams, pattern conformance, abstraction quality. Posted as a PR review comment.

Each review pass produces a structured pass/fail result. On pass, the next review runs. On fail, findings are captured for the fix loop.

### Iterative Fix Loop

When CI fails or any review pass fails, the pipeline enters a fix loop:

1. Collect all current failures: CI test failures, review findings with file/line references.
2. Create fix beads labeled with the spec. These re-enter the normal run loop and execute on the spec branch.
3. After fix beads complete, push updated branch to origin. CI re-runs automatically.
4. Re-run the full review pipeline from the beginning (Stage 1: CI, then all three review passes). Fixes may introduce new issues, so the full pipeline must re-validate.
5. Update the PR: post a comment summarizing what was fixed and what the current status is.

The fix loop is capped at a configurable limit (default: 3 cycles). If the cap is reached, the pipeline posts a summary of remaining failures and alerts the user that the spec needs manual intervention.

Each fix cycle updates the PR body's acceptance criteria status section to reflect current state.

### Non-Blocking Approval

The run loop does not wait for human approval. After all gates pass:

1. The pipeline posts a final summary comment: "All validation passed, all reviews passed. Ready for human review."
2. Requests review from configured reviewers (if `spec_pr.reviewers` is set).
3. The spec PR enters "awaiting approval" state in gromit's tracking.

Between iterations, the run loop checks open spec PRs via `gh pr view`:
- **PR merged** — clean up: delete local spec branch, update spec state, log success.
- **PR approved but not merged** — optionally auto-merge via `gh pr merge` if `spec_pr.auto_merge_on_approval` is enabled (default: false).
- **Changes requested** — if `spec_pr.auto_fix_human_comments` is enabled (default: false), parse review comments as findings and create fix beads.
- **PR closed** — mark spec as abandoned, preserve branch for manual recovery.
- **Still open** — no action, continue with other beads.

The run loop processes non-spec beads and beads from other specs while PRs are pending. Multiple spec PRs can be open simultaneously (configurable; default: concurrent).

### Merge

Merge happens through GitHub's merge mechanism (configured via `spec_pr.merge_method`: "squash", "merge", or "rebase"; default: "squash"). The pipeline does not merge locally. After merge, the spec branch is deleted (GitHub's auto-delete or explicit `gh api` call).

### Concurrent PR Policy

By default, multiple spec PRs can be open simultaneously. Each spec gets its own branch, its own PR, and its own review cycle. Merge conflicts between specs are resolved at merge time by GitHub (or by the LLM conflict resolution if rebasing is needed).

If `spec_pr.max_open_prs` is set to 1, the pipeline queues spec completions — only one PR is created at a time. Subsequent specs wait until the current PR is merged or closed.

### `gromit prs` Command

A new CLI command `gromit prs` provides a dashboard for managing open spec PRs.

**List view.** Running `gromit prs` with no arguments shows a table of all open spec PRs:

```
SPEC              PR     CI       REVIEW          BEADS   STATUS
auth-system       #42    pass     3/3 passed      0       Ready for review
payment-flow      #45    fail     1/3 (blocked)   2       Fixing (cycle 2/3)
cache-layer       #48    running  pending          0       Waiting for CI
```

Columns:
- **SPEC** — spec name
- **PR** — GitHub PR number (links to PR URL in terminal-capable environments)
- **CI** — CI status: `pass`, `fail`, `running`, `pending`
- **REVIEW** — LLM review gate status: `N/3 passed`, `pending`, `blocked` (waiting on CI)
- **BEADS** — number of in-progress fix beads for this spec
- **STATUS** — human-readable state: "Ready for review", "Fixing (cycle N/M)", "Waiting for CI", "Needs manual intervention", "Approved"

PRs that are fully ready — zero in-progress beads, CI passing, all three reviews passed — are marked as mergeable. The user can select a PR from the list and merge it directly. PRs that don't meet all three conditions cannot be merged (no `--force` override from list view).

**Detail view.** Running `gromit prs <spec-name>` or selecting a PR from the list shows:

- Full PR summary (the LLM-generated narrative from the PR body)
- CI check results with pass/fail per check
- LLM review status per stage (conformance, code quality, architecture) with finding counts
- In-progress fix beads with their titles
- Current fix cycle number and cap
- Link to the GitHub PR

**Merge action.** Available from both the list view (interactive selection) and the detail view:

- `gromit prs <spec-name> --merge` merges using the configured merge method
- Merge is only enabled when all three conditions are met: zero in-progress beads, CI passes, and all three LLM reviews pass. If any condition is unmet, the merge option is disabled with a message explaining what's blocking it.
- Uses `gh pr merge` with the configured method (squash/merge/rebase)
- After merge, cleans up the local spec branch and updates spec state

### Configuration

```yaml
spec_pr:
  enabled: true                        # Create PRs for spec completion (default: false)
  reviewers: []                        # GitHub usernames to request review from
  merge_method: "squash"               # "squash" | "merge" | "rebase"
  fix_cycle_cap: 3                     # Max fix loop iterations
  auto_fix_human_comments: false       # Pick up human review comments as fix findings
  auto_merge_on_approval: false        # Auto-merge after human approves
  ci_poll_interval: 30                 # Seconds between CI status checks
  ci_timeout: 600                      # Max seconds to wait for CI
  max_open_prs: 0                      # 0 = unlimited concurrent PRs; 1 = one at a time
```

## Acceptance Criteria

### Branch-Per-Spec Wiring

- Beads with `spec:<name>` labels execute on branch `gromit/spec-<name>`, not on main.
- Beads without a spec label execute on main.
- The orchestrator checks out the correct branch before each bead's Build stage.
- Switching between spec and non-spec beads (or between different specs) checks out the appropriate branch.
- `SpecMergeController` is wired in the constructor; `maybeTriggerSpecMerge()` fires when the last bead of a spec closes.

### PR Lifecycle

- When the last bead of a spec closes, the pipeline pushes the spec branch and creates a GitHub PR via `gh pr create`.
- The PR body contains a comprehensive, human-readable summary: spec objective, what changed (narrative), acceptance criteria status, files by package, test coverage, and known limitations.
- The PR summary is generated from the actual diff and spec document, not templated boilerplate.

### CI and Review

- CI failures are detected via `gh pr checks` and fed into the fix loop.
- Three LLM review passes (conformance, code quality, architecture) run in order as hard gates.
- Review findings are posted as GitHub PR review comments (inline where possible).
- On any failure (CI or review), fix beads are created and the full pipeline re-runs after fixes complete.
- The fix loop is capped at the configured limit; exceeding it posts a failure summary and alerts the user.

### Non-Blocking Approval

- After all gates pass, the pipeline posts a "ready for review" comment and requests human review.
- The run loop continues processing other beads while PRs await approval.
- Between iterations, the run loop polls open spec PRs and handles merged/approved/closed/changes-requested states.
- Multiple spec PRs can be open concurrently (by default). Setting `max_open_prs: 1` enforces sequential PR processing.

### `gromit prs` Command

- `gromit prs` lists all open spec PRs with columns: spec name, PR number, CI status, review gate status, in-progress fix bead count, and human-readable status.
- `gromit prs <spec-name>` shows the full PR summary, CI check results, per-stage review status, fix bead details, and a link to the GitHub PR.
- `gromit prs <spec-name> --merge` merges the PR using the configured merge method, cleans up the local spec branch, and updates spec state.
- Merge is available from both list and detail views, but only enabled when all conditions are met: zero in-progress beads, CI passes, and all three LLM reviews pass.

### Merge and Cleanup

- The PR is not auto-merged by default. Human approval via GitHub review UI or `gromit prs --merge` is required.
- If `auto_merge_on_approval` is enabled, the pipeline merges after human approval.
- Merge uses the configured merge method (squash/merge/rebase) via GitHub, not local git.
- The spec branch is deleted after successful merge.
- Each fix cycle updates the PR with a status comment and refreshes the acceptance criteria section.

## Decisions

1. **This spec subsumes spec-branch-merge-pipeline wiring.** The branch routing, constructor injection, and Trigger implementation are prerequisites that make no sense to ship independently. They're included here as Part 1 so everything ships as a working feature.

2. **GitHub PR as the merge mechanism, not local git.** PRs provide visibility, audit trail, CI integration, and team collaboration. Local rebase+merge is invisible. Branch protection rules and required checks can enforce quality gates independently of gromit.

3. **Non-blocking approval.** The run loop continues processing other beads while PRs await approval. Blocking would waste compute on idle polling. Between-iteration PR status checks are cheap and natural.

4. **Concurrent PRs by default.** Specs are independent units of work. Serializing them creates an artificial bottleneck. Cross-spec conflicts are handled at merge time, same as any multi-PR workflow.

5. **Full pipeline re-run after fixes.** Fixes can introduce regressions. Re-running from CI (not from the failing review stage) ensures nothing slips through.

6. **Human approval required, no auto-merge by default.** The point is quality assurance. The human sees the full picture — diff, reviews, CI, summary — and makes the call. Auto-merge is opt-in for teams that trust the automated gates.

7. **Squash merge as default.** Spec branches contain many small bead commits and fix iterations. Squashing into a single commit on main keeps history clean. The PR preserves the full commit history for archaeology.

8. **Summary is LLM-generated from diff, not templated.** The LLM reads the actual changes and spec, producing a summary that tells the reviewer what actually happened and why.

9. **Fix beads re-enter the normal run loop.** Reuses all existing build/validate infrastructure. Fix work is visible in bead tracking. The spec branch receives the fixes naturally since those beads are spec-labeled.

10. **CI as first gate, before LLM reviews.** No point reviewing code that doesn't compile or pass tests. CI is fast and definitive; LLM reviews are slower and more nuanced.

11. **Review findings as PR comments, not just pass/fail.** Inline comments on specific lines give the human reviewer (and fix beads) precise context. The PR becomes a complete record of all review feedback.

12. **`gromit prs` as the local dashboard.** GitHub's PR UI is comprehensive but requires context-switching to a browser. `gromit prs` gives the developer a terminal-native view of all spec PRs with the information they need to decide: merge, wait, or intervene. The merge action avoids round-tripping to the browser for a simple approval.

## Research & Context

### Current State

The spec-branch-merge-pipeline defined the branch-per-spec lifecycle and a 4-stage internal merge pipeline. The infrastructure is partially implemented but not connected:

- `internal/runner/specbranch/` — Router (`BranchForLabels()`) and GitOps (create/checkout, rebase, merge, delete, `ConflictError`). Fully built, never called by the orchestrator.
- `internal/runner/specmerge/` — Pipeline skeleton with `IsSpecComplete()`, three review stages, merge operations with conflict resolution. `Trigger()` is a stub returning nil.
- `orchestrator.go` — `maybeTriggerSpecMerge()` is called at line 310 after each successful epilogue but no-ops because `SpecMergeController` is never injected in the constructor.
- `Orchestrator` struct has no `Router` field — no way to resolve branches before bead execution.
- Config — `MethodologyGranularitySpec` is recognized and validated. `GitConfig` (auto_push, push_failure, push_timeout) is fully implemented in config layer but `git push` execution code does not exist.
- No `gh` CLI usage anywhere in the codebase. No GitHub API integration exists.

### Wiring Gaps (Addressed by Part 1)

| Gap | What exists | What this spec adds |
|-----|-------------|---------------------|
| Branch checkout | Router + GitOps built | Router field on Orchestrator; checkout call between Gate and Build |
| SpecMergeController | Field declared in OrchestratorConfig | Constructor wires `specmerge.Pipeline` into it |
| Trigger() | Stub returns nil | Full implementation: push, create PR, initiate review |
| Git push | Config layer complete, no execution code | `git push` via exec for branch pushing |
| GitHub CLI | Not used anywhere | `gh pr create`, `gh pr checks`, `gh pr view`, `gh pr review`, `gh pr merge` |

### Dependencies

- `gh` CLI must be available and authenticated.
- GitHub repository must have push access for the gromit user.
- Branch protection rules on main are compatible but not required — the pipeline enforces its own gates.
- CI must be configured on the GitHub repository (GitHub Actions, or any CI that reports status checks on PRs).
