# Filtered Learning Hash Eviction

## Specification

`FilteredLearningHashes` in `state.json` tracks which provisional learnings have been evaluated by the LLM quality filter, so they aren't re-evaluated on subsequent retro runs. Currently, hashes are only ever appended and never removed. Over time, hashes accumulate for learnings that are no longer provisional (promoted to confirmed, archived as generic, removed, or consolidated).

The fix reconciles the hash set against the current provisional learnings after each filter pass. Any hash in `FilteredLearningHashes` that does not correspond to a current provisional learning is pruned. This naturally bounds the set size to the number of provisional learnings (typically under 10-20).

The reconciliation runs at the end of `retro.Run()`, after `FilterProvisional` has completed (so archived learnings are already removed from the provisional list). The caller collects current provisional hashes, passes them to a new `ReconcileFilteredHashes` method on `state.File`, and saves state once with both the newly added hashes and the pruned stale ones.

## Acceptance Criteria

- After `retro.Run()` completes, `FilteredLearningHashes` in state contains only hashes that match current provisional learnings (no stale entries for archived, confirmed, or removed learnings).
- A new `ReconcileFilteredHashes(currentHashes map[string]bool)` method on `state.File` prunes hashes not present in the provided set.
- Existing unit tests for `AddFilteredHashes` and persistence continue to pass.

## Decisions

1. **Reconcile over TTL or hard cap.** The hash set exists solely to prevent re-evaluating provisional learnings. Once a learning leaves provisional, its hash is dead weight. Reconciling against current provisionals is the exact solution — no arbitrary limits needed.

2. **Reconcile after FilterProvisional, not during.** Running reconciliation after the filter pass ensures we see the final state of provisional learnings (with any newly archived ones already removed). This avoids ordering issues.

3. **Single save after both add and prune.** The caller in `retro.Run()` should add new hashes and reconcile before calling `Save()`, avoiding two separate writes.

## Research & Context

### Current State

- `FilteredLearningHashes` is a `[]string` field on `state.State` (`internal/state/state.go:19`).
- `GetFilteredHashes()` returns a `map[string]bool` for O(1) lookup (`internal/state/state.go:180-188`).
- `AddFilteredHashes()` deduplicates and appends new hashes (`internal/state/state.go:192-208`).
- `retro.Run()` loads filtered hashes, passes them to `FilterProvisional`, then saves new hashes (`internal/retro/retro.go:91-116`).
- `FilterProvisional()` in `internal/learnings/learnings.go:492-547` iterates provisional learnings, skips already-filtered ones, classifies new ones, archives generics, and returns newly-evaluated hashes.
- Learning hashes are 16-char hex strings (first 8 bytes of SHA256), generated by `hashContent()` in `internal/learnings/learnings.go:562-569`.
- Current provisional learnings are accessible via `File.GetProvisional()` which returns `[]Learning`, each with a `.Hash` field.
