# Spec 0004h — Contract Correction Validation Against Spec ACs

## spec_id
0004h-contract-correction-validation

## Depends on
0004f-contract-specificity-validation

## Vision

Contract auto-correction silently rewrites assertion paths to point at sibling files that happen to contain the pattern. When the spec's acceptance criteria explicitly name a file (e.g., "keep test X in file Y"), the corrector can redirect the contract away from Y to a different file Z — creating a direct contradiction between the contract and the spec. The executor then thrashes: the reviewer says "delete Z, the spec says Y" but the contract demands Z exist. This is the #1 cause of executor thrash loops.

## Summary

Before committing a contract correction, validate that the new path does not contradict the spec's acceptance criteria. If the AC text explicitly references the original path, reject the correction and keep the original contract path. This is a guard clause added to `attemptContractCorrection` in `validate.go`, not a new subsystem.

## Goals

### Primary
- Prevent contract corrections that contradict spec acceptance criteria
- Eliminate the thrash loop where executor oscillates between contract demands and reviewer/spec demands

### Secondary
- Emit a clear event when a correction is rejected so the loop has observability into why

## Non-goals
- Full semantic alignment between contracts and specs (too broad; this is a targeted guard)
- Changing how contracts are initially generated by the LLM in WriteContracts
- Validating contract corrections against anything other than the AC section of the spec
- Handling cases where ACs reference paths indirectly or via glob patterns

## Architecture

All changes are localized to `internal/next/specloop/stages/validate.go` and a small helper.

### Guard clause in `attemptContractCorrection`

Before accepting a sibling-file correction (the `found != ""` branch around line 300), check whether the spec's acceptance criteria text mentions the original path (`oldPath`). If it does, skip the correction — the spec author intentionally named that file — and add the failure to `remaining` instead.

### AC path extraction

Add a function `specACMentionsPath(specText, path string) bool` that:
1. Extracts the Acceptance Criteria section from the spec markdown (text between `## Acceptance Criteria` and the next `##` heading)
2. Checks whether the AC text contains the basename of `path` as a substring

Basename matching is sufficient because specs reference files by name (e.g., `write_contracts_test.go`), not full relative paths. This avoids false negatives from path prefix differences.

### Config change

`ValidateStageConfig` needs a `SpecText string` field (or `SpecPath string` that is read once at stage construction). The spec text is already available in the pipeline — it is read for scenario parsing in `WriteScenarioTestsStage`. Thread it through to `ValidateStage` the same way.

### Event emission

When a correction is rejected, emit a `contract_correction_rejected` event with the scenario name, original path, candidate path, and reason ("spec AC references original path").

## Acceptance Criteria

1. `attemptContractCorrection` skips a correction when `specACMentionsPath` returns true for the original path, leaving the failure in the `remaining` slice
2. `specACMentionsPath` extracts the AC section and checks for the file's basename as a substring; returns false when AC section is empty or missing
3. A `contract_correction_rejected` event is emitted when a correction is rejected, containing scenario name, old path, candidate path, and reason
4. `ValidateStageConfig` accepts spec text (directly or via path) so the guard clause can access AC content
5. Existing contract correction behavior is unchanged when the spec ACs do not mention the original path
6. When spec text is empty or not provided, the guard is a no-op (all corrections proceed as before — backward compatible)

## Scenarios

### Scenario: correction rejected when AC names original file
**Given:** A spec with AC text containing "keep StructuralRegression test in write_contracts_test.go", a contract with a `file_contains` assertion pointing at `write_contracts_test.go`, and a sibling file `stages_scenario_structural_regression_test.go` that contains the pattern
**When:** `attemptContractCorrection` runs
**Then:** The correction is rejected, the contract still points at `write_contracts_test.go`, a `contract_correction_rejected` event is emitted, and the failure remains in the `remaining` slice

### Scenario: correction proceeds when AC does not mention original file
**Given:** A spec with AC text that does not mention `foo_test.go`, a contract with a `file_contains` assertion pointing at `foo_test.go`, and a sibling file `bar_test.go` that contains the pattern
**When:** `attemptContractCorrection` runs
**Then:** The correction proceeds normally, the contract is updated to point at `bar_test.go`, and a `contract_corrected` event is emitted

### Scenario: guard is no-op when spec text is empty
**Given:** `ValidateStageConfig.SpecText` is empty, and a contract correction would normally be applied
**When:** `attemptContractCorrection` runs
**Then:** The correction proceeds as before (backward compatible)

### Scenario: basename matching handles path prefix differences
**Given:** A spec AC says "keep tests in write_contracts_test.go" and the contract assertion path is `internal/next/specloop/stages/write_contracts_test.go`
**When:** `specACMentionsPath` is called with the full relative path
**Then:** It returns true because the basename `write_contracts_test.go` appears in the AC text
