# Spec 0003h — Contract File Self-Correction

## spec_id
0003h-contract-file-self-correction

## Depends on
0003g-contract-loop-detection

## Vision
Contracts are generated by an LLM before implementation begins. The LLM
predicts which file will contain a given pattern, but the implementation
may correctly place code in a sibling file instead (e.g., `spec_test.go`
instead of `exec_test.go`). The result is a contract that will never pass,
not because the implementation is wrong, but because the contract's file
path is wrong. This causes either an infinite replan loop (addressed by
0003g) or unnecessary human intervention. The system should be able to
recognize and correct this class of error autonomously.

## Summary
When a `file_contains` assertion fails, the validate stage searches sibling
`.go` files in the same package directory for the pattern before propagating
the failure. If found, the contract YAML is updated in-place, a
`contract_corrected` event is emitted, and evaluation re-runs with the
corrected contract — no replan triggered. If the pattern is not found
anywhere in the directory, the failure propagates as normal.

## Goals
### Primary
- Auto-correct `file_contains` assertions that point to the wrong file when
  the pattern exists in a sibling file in the same directory
- Emit a `contract_corrected` event per corrected assertion recording the
  old path, new path, and pattern
- Re-evaluate the corrected contract without triggering a replan

## Non-goals
- Correcting wrong pattern values — a pattern that exists nowhere is a
  genuine implementation mismatch, not a metadata error
- Searching outside the package directory (no recursive or cross-package search)
- Correcting non-`file_contains` assertion types
- Correcting `file_not_contains` assertions

## Architecture

### Validate Stage

After the initial `s.contractEvaluator.Evaluate()` call, the validate stage
runs a correction pass over any `file_contains` failures before propagating
them. For each failure:

1. Extract the failing file path and pattern from the `ContractFailure`
2. Search all `.go` files in `filepath.Join(workDir, filepath.Dir(failingPath))`
   for the pattern
3. If found in a sibling file, update that assertion's `path` in the
   in-memory `ScenarioContract` and rewrite the YAML to disk
4. Emit a `contract_corrected` event

After all corrections, re-run `Evaluate()` with the updated contract. The
second evaluation result is used for the rest of the validate stage logic.

### New event type

```go
type ContractCorrectedEvent struct {
    BaseEvent
    ScenarioName string `json:"scenario_name"`
    OldPath      string `json:"old_path"`
    NewPath      string `json:"new_path"`
    Pattern      string `json:"pattern"`
}
```

### ContractEvaluator

No changes — the correction pass lives in the validate stage, not the
evaluator. The evaluator remains a pure evaluator.

### Contract YAML rewrite

The corrected YAML is written back to `scenario-contracts.yaml` in
`EvidenceDir`. The in-memory `ScenarioContract` is updated before the second
`Evaluate()` call so both file and in-memory state are consistent.

## Acceptance Criteria

1. When a `file_contains` assertion fails and the pattern exists in a sibling
   `.go` file in the same directory, the contract is updated and evaluation
   re-runs without triggering a replan
2. When a `file_contains` assertion fails and the pattern does not exist in
   any file in the same directory, the failure propagates to replan as normal
3. One `contract_corrected` event is emitted per corrected assertion,
   recording `scenario_name`, `old_path`, `new_path`, and `pattern`
4. The corrected `scenario-contracts.yaml` is written to disk so subsequent
   resumes use the corrected contract
5. When multiple assertions need correction, all are corrected in a single
   pass before re-evaluation
6. Non-`file_contains` assertion types are not affected
7. When the corrected contract still has failures after re-evaluation, those
   failures propagate to replan as normal
8. All existing validate stage tests continue to pass

## Scenarios

### Scenario: file_contains assertion corrected to sibling file
**Given:** A contract asserts `pattern: "feature/beta-branch"` in
`cmd/gromit-next/exec_test.go`. The pattern does not exist in `exec_test.go`
but does exist in `cmd/gromit-next/spec_test.go`.
**When:** The validate stage runs and initial evaluation returns a
`file_contains` failure for that assertion
**Then:** The contract is updated to point to `spec_test.go`. A
`contract_corrected` event is emitted with `old_path: "cmd/gromit-next/exec_test.go"`,
`new_path: "cmd/gromit-next/spec_test.go"`, `pattern: "feature/beta-branch"`.
The second evaluation finds no failure for that assertion. No replan triggered.

### Scenario: pattern not found anywhere — failure propagates
**Given:** A contract asserts `pattern: "feature/foo"` in
`cmd/gromit-next/exec_test.go`. The pattern does not exist in `exec_test.go`
or any sibling file in that directory.
**When:** The validate stage runs and initial evaluation returns a failure
**Then:** No correction is made. The failure propagates to `ReplanFrom`.
No `contract_corrected` event is emitted.

### Scenario: multiple assertions corrected in one pass
**Given:** A contract has 3 failing `file_contains` assertions, all pointing
to `exec_test.go`, with patterns that exist in `spec_test.go`.
**When:** The validate stage runs
**Then:** All 3 assertions are corrected before re-evaluation. 3
`contract_corrected` events are emitted. The second evaluation passes for
all 3. No replan triggered.

### Scenario: correction fixes some but not all failures
**Given:** A contract has 2 failing assertions: one where the pattern exists
in a sibling file, one where the pattern exists nowhere.
**When:** The validate stage runs
**Then:** The correctable assertion is fixed and a `contract_corrected` event
emitted. The uncorrectable assertion still fails after re-evaluation.
`ReplanFrom` is returned with only the uncorrectable failure.
